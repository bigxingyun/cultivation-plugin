## 一、为什么需要这份计划

用户的目标链是：

```
现在：读 Koishi 官方开发指南 → 写成开发指南
  ↓
然后：完成游戏的设计
  ↓
最后：总结成一份《项目开发指南》
  ↓
日后：开新工作区，新对话仅凭这些文档独立完成插件开发
```

关键约束是**最后一步**：那份《项目开发指南》必须做到"**新对话不依赖本会话的任何上下文**"也能开发。这决定了整份计划的组织方式——不是写给人看的综述，而是写成**可执行的规范**：公式、表结构、指令清单、断言、验收标准。

因此本计划有一条贯穿始终的原则：

> **凡是能被写成一个公式或一条断言的，就不要写成一段描述。**

### 3.2 ❌ 发现 4 处缺陷（必须在写内容文档前修掉）

#### 缺陷 1：`§4.6` 表中 `EP(73)` 录错（2.5 倍偏差）

| | 值 |
| --- | --- |
| 文档 §4.6 写 | `1,534,841` |
| 按文档自己的公式算 | `3,837,102` |
| 偏差 | **2.50 倍** |

**根因**：`1,534,841 = 2.5 × 17.0 × T(73)`，即有人把"金仙段的参考倍率 17.0"当成**常数**代入了，而正确做法是按锚点插值（金仙段起点 R = 2.5 × 17.0 = 42.5，`EP(73) = 42.5 × T(73) = 3,837,102`）。

**影响面**：只此一格。`§4.6` 其余 9 格、境界 EP 合计、任务链奖励全部基于正确公式，**未受影响**。

#### 缺陷 2：`§7.1` 的 `req` 系数列与成功率列互不相容（最严重）

| 档位 | 文档「系数」 | 用系数算出的成功率 | 文档表里写的成功率 | 由成功率反解的 `req/punch` |
| --- | --- | --- | --- | --- |
| 凡 | 0.5 | 95.0% | 95.0% | （截断） |
| 黄 | 0.7 | **95.0%** | 95.0% | （截断） |
| 玄 | 1.0 | **95.0%** | **76.0%** | 1.250 |
| 地 | 1.4 | **84.1%** | **68.7%** | 1.471 |
| 天 | 1.9 | **70.1%** | **63.0%** | 1.680 |
| 仙 | 2.5 | **58.5%** | **58.1%** | 1.892 |
| 帝 | 3.2 | **49.0%** | **53.6%** | 2.121 |

**两列无法同时成立**。另外 `§7.4` 的示例字段写 `"req_coef": 0.5`，但要让凡档成功率达 95% 并让玄档落在 76%，基准比例其实是 **0.75**，不是 0.5。

**影响面**：这是**玩法手感的核心参数**（玩家每次历练的成功率），也是 `§7.1` 那张表最有价值的一列。必须定死。

#### 缺陷 3：`§10.1` 修为丹「占该层 EP 5%–24%」不成立

实算（按文档自己的公式）：

| 丹药品级 | 丹值 | 所在境界 EP 区间 | 占区间首 | 占区间末 |
| --- | --- | --- | --- | --- |
| 一品 | 1,000 | 16,500 → 31,640 | 6.06% | 3.16% |
| 二品 | 2,500 | 34,323 → 64,516 | 7.28% | 3.88% |
| 三品 | 6,000 | 69,811 → 130,257 | 8.59% | 4.61% |
| 四品 | 15,000 | 140,819 → 260,008 | 10.65% | 5.77% |
| 五品 | 40,000 | 280,722 → 510,480 | 14.25% | 7.84% |
| 六品 | 100,000 | 550,100 → 982,420 | 18.18% | 10.18% |
| 七品 | 250,000 | 1,056,281 → 5,131,371 | 23.67% | **4.87%** |

真实区间是 **3.2% – 23.7%**，且七品丹跨越两个大境界导致占比从 23.7% 崩到 4.9%。文档写的"5%–24%"是取了两端，中段被抹平了。

#### 缺陷 4：`§15` 断言 7 的 `E(0.1) ≈ 6.1` 是陈旧残留

按文档自己的公式 `E(0.1) = 2.1919`，不是 6.1。**但文档其余部分全部使用 2.153/1.424/1.025 等正确值**，所以只是那一条断言没跟着更新。

#### 1.1 研究阶段已确认的硬约束（代理 C 反馈，直接改变设计）

| 约束 | 影响 |
| --- | --- |
| **QQ 官方机器人是被动型平台**：每天只能发**极少**主动消息；被动消息必须在用户发言后**短时间内**回复 | 🔴 **设计已相应修改**（见 `开发游戏设定.md §9.7` 新增的平台约束块）：**零主动推送也能玩**、每日重置与离线结算**惰性计算**、突破提示改为**玩家下次发言时被动带出**。定时推送降级为默认关闭的可选优化 |
| **`ctx.database` 不是内置服务** | 插件必须 `export const inject = ['database']` |
| **官方无默认数据库** | 需从 5 个驱动中选一个（`memory` 是唯一零配置；正式用 `sqlite`，默认 `data/koishi.db`） |
| **`ctx.model.extend` 没有 `index` 参数** | `Table.Meta` 只有 `primary`/`unique`/`foreign`/`autoInc`。`mission_queue` 按 `finishAt` 索引的需求**要靠 `unique` 变通或改查询方式** |
| **字段类型只有 12 种** | `'boolean'` 不在官方类型表中（却出现在官方 migrate 示例里）——本项目布尔量用 `unsigned`/`integer` 存 0/1 |
| **`string` 默认仅 255 字节** | 任务/故事文本必须用 `text` 或显式 `length` |
| **查询操作符无 `$exists`/`$prefix`/`$expr`**；无 `aggregate()` | 聚合走 `ctx.database.eval()` 或 `Selection.execute(expr)` |
| **观察者字段必须先声明** | `session.user` 上未声明的字段读不到也改不了 → 需 `userFields()` 或 `before('attach-user', ...)` |
| **`dispose` 不保证执行** | 每次数据变更**立即写库**，不做"退出时统一存档" |
| **`ctx.database.get()` 永远返回数组**；`set()` 不插入；`create()` 主键冲突报错；`upsert()` 返回值文档自相矛盾 | 实现时按 API 页原文（`Promise<WriteResult>`）为准，并对该矛盾点在代码里加注释 |
| **官方无 cron** | 只有 `ctx.setTimeout/setInterval/sleep/throttle/debounce`。`koishi-plugin-cron` 是社区插件 |

#### 1.2 研究结论中"必须写进指南"的负向清单

新对话最容易犯的错是**臆造 API**。指南要单列一节"**不存在的 API**"：

- ❌ `export const schema`（应为 `export const Config: Schema<Config>`）
- ❌ `boolean` / `guild` / `member` 参数类型；❌ `cmd.shortcut()`（v1 API）；❌ `session.reply()`
- ❌ `before-command` / `connect` / `disconnect` 事件名（应为 `command/before-execute`、`login-added` 等）
- ❌ `$exists` / `$prefix` / `$expr` 查询操作符；❌ `ctx.database.aggregate()`；❌ `ctx.model.extend` 的 `index` 参数
- ❌ 注册自定义参数类型的 API（只有**选项**支持 `config.type`）
