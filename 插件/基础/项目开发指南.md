## 第一章 这是什么项目

一个 **Koishi 平台的 QQ 机器人插件**，实现一款**文字修仙挂机（放置）游戏**。

**一句话玩法**：玩家在群里发指令闭关挂机，修为随时间累积；攒满经验池后突破境界；用每日有限的历练次数换取功法、丹药与材料；推任务链读长篇故事。**全程纯文字，没有图形界面。**

**核心乐趣定位**（这句话决定了所有设计取舍）：

> **增量 + 看故事。**
> 增量由数值曲线负责（闭关是主基调，占全程 73%），故事由任务链负责（18 条链 / 108 个节点 / 约 7.2 万字）。

**周期目标**：满级 81 层，纯挂机 890 小时（37.1 天），含突破失败折损 **1,464 小时 ≈ 61 天**。
**"满历练一个月"**：历练次数上限在第 25 天左右（人仙境）全部解锁完毕。

### 1.1 技术形态

| 项 | 值 |
| --- | --- |
| 平台 | Koishi（TypeScript 插件） |
| 目标群 | QQ（官方适配器） |
| 界面 | **纯文字**。无图片、无按钮、无卡片 |
| 交互入口 | 约 15 条指令（见第六章） |
| 数据 | Koishi 数据库（推荐 `sqlite`） |

### 1.2 三条必须先知道的硬约束

1. **QQ 官方机器人是被动型平台**——"每天只能发送极少量的主动消息"。**整个游戏必须做到"零主动推送也能玩"**：每日重置与离线结算一律**惰性计算**（按时间戳），突破提示改为玩家下次发言时被动带出。详见 `koishi开发要点.md` §8.3。
2. **`dispose` 不保证执行**。官方警告：进程崩溃或强杀时可能不触发。**每次数据变更立即写库**，绝不做"退出时统一存档"。详见 `koishi开发要点.md` §2.5。
3. **禁止硬编码数值表**。所有曲线必须**由公式现算**。文档里的表格都是"按公式实算后取整"，是给人看的。详见本文章。

#### 3.3.1 本次实测踩到并已确认的坑（**§3.2 的原始命令序列缺了这几步**）

| # | 坑 | 症状 | 正确做法 |
| --- | --- | --- | --- |
| 1 | **不要单独安装 `@koishijs/cli`** | 它会把陈旧的 `@koishijs/loader@2.6.2` + `cordis@2.x` 提升到顶层，与 `koishi@4.18.11` 需要的 `loader@4.6.11`、`cordis@3.18.1` 打架，报 `cannot resolve plugin`、`Cannot set property name of #<_MainScope>`、`this.runtime.using.every is not a function` | 用 `koishi` 包自带的 `bin.js`（即 `koishi start`），**只依赖 `koishi`** |
| 2 | `data/` 目录必须先存在 | sqlite 驱动报 `The database directory 'E:\koshi\data' is not accessible`，且**数据库服务静默不注入**（`ctx.database` 为 undefined，插件被 `inject` 卡住不加载） | 先 `mkdir data`；或改用 memory 驱动 |
| 3 | 工作区插件必须有构建产物 | `ns-require` 解析到包后要读 `main`（`lib/index.js`），`lib/` 不存在就报 `cannot resolve plugin "demo"` | 改完源码先 `npm run build`；本工作区 `npm run dev` 已内置这一步 |
| 4 | `logger` **不是内置插件** | `cannot resolve plugin "logger"` | `npm i @koishijs/plugin-logger` |
| 5 | `@koishijs/client` 是 console 的 **peer 依赖**，npm 不会自动装 | console 报 `Cannot find module '@koishijs/client/package.json'`，控制台无法渲染 | `npm i @koishijs/client`（版本需与 console 同号） |
| 6 | `dispose` 里不能用 `ctx.logger()` | 卸载时抛 `ctx.logger is not a function` | 模块顶层 `const logger = new Logger('x')`，之后一直用它 |
| 7 | 假消息不能传 `content: '裸字符串'` | payload 的属性会覆盖 Session 原型上的 `content` setter，`session.stripped.content` 变成 `undefined`，前缀解析抛 `Cannot read properties of undefined (reading 'startsWith')` | 传 `h('text', { content })`，或直接用官方 `@koishijs/plugin-mock` |
| 8 | 官方 `mock` 插件的模块形态 | `require('@koishijs/plugin-mock')` 拿到的是 CJS 包装对象，插件本体在 `.default` 上 | `mod.default ?? mod` |

> ⚠️ **第 1 条与 §2 的原文冲突吗？** 不冲突。`koishi开发要点.md` 给出的是**官方文档事实**，
> 而这条是**本次实测的依赖解析结论**：单独装 CLI 会让版本拓扑退化。文档没写错，只是不够。

> ⚠️ **一个容易误判的现象**：`koishi.yml` 里写错的插件名，加载器**只打一行错误就跳过**，
> 应用照常启动、控制台照常打开。**判断插件到底加载了没有，看启动日志里的
> `loader apply plugin <名字>`**——没出现就是没加载。

> ⚠️ **`koishi.yml` 会被应用自动改写**：Koishi 启动时会给每个插件项补一个随机后缀（如
> `logger:syo61k`）、并往 `package.json` 里补写它依赖的插件。**这是正常行为**，不要去"修正"。
> 本次它自动补了 `@koishijs/plugin-http`、`@koishijs/plugin-proxy-agent`。

## 第五章 核心算法（**最关键的一章**）

> **总原则：凡是公式能算出来的，就不要硬编码表格。**
> 文档里的每一张表都是"按公式实算后取整"，是给人看的。代码必须现算。

### 5.1 四个核心函数

```ts
const RATIO = 1.037          // 核心公比，全项目唯一

// 1) 单层挂机耗时（秒）—— 节奏的唯一来源
function T(rank: number): number {
  return 6600 * Math.pow(RATIO, rank - 1)
}

// 2) 裸属性（最大生命与攻击同值）
function attr(rank: number): number {
  return 100 * Math.pow(RATIO, rank - 1)
}

// 3) 修为增速（每秒）—— 锚点分段插值
const ANCHORS = [1.0, 1.5, 2.2, 3.2, 4.6, 6.5, 9.0, 12.5, 17.0]

function mult(rank: number): number {
  const qi = Math.floor((rank - 1) / 9)          // 大境界索引 0..8
  if (qi >= 8) return ANCHORS[8]                  // 金仙段恒为 17.0
  const qf = ((rank - 1) % 9) / 9                 // 段内插值位置 0..1
  return ANCHORS[qi] * Math.pow(ANCHORS[qi + 1] / ANCHORS[qi], qf)
}

function R(rank: number): number {
  return 2.5 * mult(rank)                         // R(1)=2.5, R(81)=42.5
}

// 4) 经验池（派生量，不是调参旋钮）
function EP(rank: number): number {
  return R(rank) * T(rank)
}
```

**关键约束**：

| 约束 | 值 | 违反后果 |
| --- | --- | --- |
| `T` / `attr` 公比必须同值 | **1.037** | 成功率不再跨 rank 恒定，`punch = 3×生命` 崩 |
| 金仙段 `mult` 恒为 17.0 | 是 | `EP(73)` 会变成 2.5 倍（**这个错误真实发生过**） |
| `R` 必须在 `2.5` 到 `42.5` 之间单调 | 是 | 成长感受损 |

**基准值自查**（实现后必须能复现这些数）：

| rank | `T` | `attr` | `R` | `EP` |
| --- | --- | --- | --- | --- |
| 1 | 6,600 s | 100 | 2.5 | **16,500** |
| 9 | 8,826 s | 134 | 3.585 | **31,640** |
| 18 | — | 185 | 5.271 | **64,516** |
| 45 | — | 495 | 15.638 | **510,480** |
| 81 | 120,738 s | 1,829 | 42.5 | **5,131,371** |

function punch(rank: number): number {

### 5.3 突破

**概率**（`开发游戏设定.md` §5.1）：

```ts
// g = 大境界序号 1..9；k = 该境界内第几次突破 1..9（k=9 即跨境界）
function breakthroughChance(g: number, k: number): number {
  const p = 100 - 10 * (g - 1) - (10 / 9) * (k - 1)
  return Math.min(0.95, Math.max(0.05, p / 100))
}
```

**时间成本**（§5.3，决定总周期，**务必按公式实现**）：

```ts
function expectedAttempts(p: number): number {
  return 0.3 + 0.7 / (1 - 0.7 * (1 - p))
}
// E(1)=1  E(0.95)=1.0254  E(0.461)=1.4241  E(0.111)=2.1529  E(0.1)=2.1919
// ⚠️ 成本上限约 2.33 倍（p→0），不是 10 倍
```

> ⚠️ 文档曾残留 `E(0.1) ≈ 6.1`，那是**废弃公式的残留值**，已修正。

**连败保护**：同一层内连续失败 3 次，第 4 次 +15pt。突破成功或换层即重置。
**突破丹**：加算后 `min(0.95, ·)`。**概率已 ≥95% 时拒绝服用并提示**。

### 5.4 历练成功率

**权威是"目标成功率"，`req` 由反解公式生成**（这条曾经出过严重 bug）：

```ts
// 七档的目标成功率（权威值）
const TARGET = [0.95, 0.95, 0.76, 0.687, 0.63, 0.581, 0.536]

// 反解 req —— 实现 req 时用这条，不要手抄数字
function reqFor(target: number, punch: number): number {
  return punch * (1.9 / target - 1) / 1.2
}

function successChance(punch: number, req: number): number {
  return Math.min(0.95, Math.max(0.05, 1.9 * punch / (punch + 1.2 * req)))
}
```

**反解出的 `req_coef`**（= `req/punch`）：`0.833 / 0.833 / 1.250 / 1.471 / 1.680 / 1.892 / 2.121`

> ⚠️ **这两组数字曾经互不相容**：旧文档的难度列写 `0.5/0.7/1.0/1.4/1.9/2.5/3.2`，而成功率表对应的却是上面这组。**照哪一列写都会错。** 现在统一为"目标成功率为权威"。断言 18 锁这一点。
> 💡 凡 / 黄两档都是 95%（上限），靠**收益**区分（0.03 vs 0.06 倍 EP、掉落 50% vs 70%），不是靠难度。

**任务耗时**：`T(rank) * 1.5^(档位-1)`（档位 1..7）。

### 5.5 离线结算（**本项目最容易做错的地方**）

```ts
// ❌ 错误：用定时器每秒累加
//   —— Koishi 进程重启 / 崩溃就全丢（官方 dispose 警告）

// ✅ 正确：全部用时间戳，读数据时惰性结算
function settleSeclusion(user: User, now: number): void {
  if (!user.seclusionStart) return
  const seconds = Math.floor((now - user.seclusionStart) / 1000)
  if (seconds <= 0) return
  user.exp += seconds * R(user.rank) * techniqueMul(user) * pillMul(user)
  user.seclusionStart = now          // 结算到此刻
  // ⚠️ 立即写库，不要攒着
}
```

**三条铁律**：

1. **每日重置按服务器日期比较**（`YYYY-MM-DD`），**不要用**"距上次登录 > 24h"。
2. **首次结算前先取当前 rank 的 `R`**，不要用一个过期的缓存值。
3. **结算完立即 `set`/`upsert`**。见 `koishi开发要点.md` §6.7。

### 5.6 原子扣减（并发安全）

扣历练次数、扣材料、扣丹药**必须**用这个范式，不能"先 get 再 set"：

```ts
import { $ } from 'koishi'

const result = await ctx.database.set(
  'user',
  { id: userId, missionQuotaUsed: { $lt: dailyQuota } },
  (row) => ({ missionQuotaUsed: $.add(row.missionQuotaUsed, 1) }),
)
if (!result.matched) return '今日历练次数已用完。'
```

> `matched` 是**匹配的行数**（不是修改的行数）。0 表示条件不满足，即扣减失败。

## 第九章 红线（不许做的事）

`开发游戏设定.md` §12 有完整红线表。以下是**最容易被无意违反**的：

| 红线 | 值 | 违反后果 |
| --- | --- | --- |
| 突破成功率上限 | 95% | 突破丹失去价值 |
| 突破成功率下限 | 5% | 玩家失去希望 |
| 闪避率上限 | 40% | 成功率公式失效 |
| 同时生效功法 | **1 门** | 修正不叠加是全部平衡的前提 |
| 每日同品级丹药 | 3 次 | 丹药不能替代闭关 |
| 任务链**消耗每日次数** | **绝对不许** | 逼玩家在"刷日常"和"推故事"间二选一 |
| 任务链**掷骰** | **绝对不许** | 故事是奖励，不该被概率挡住 |
| 任务链修为系数 | 该境界 EP 合计 × 6% | 超了就成"速通捷径" |
| 灵材种类 | **只有 1 种** | 多资源把日常变成整理背包 |
| 离线收益上限 | **不设** | 原则 8：不惩罚离线 |
| 每日**必做**操作 | ≤5 分钟 | 日常不能变成负担 |
| **硬编码数值表** | **禁止** | 表格与公式必然漂移 |

**三条设计原则**（`§3`，数值层面的硬约束）：

1. **节奏与数值分离**——`T(n)` 是独立旋钮，`EP` 是派生量。不要把调参压力放到 `EP` 上。
2. **三层修正分工**——境界只给基础成长 / 功法只给修正系数 / 丹药只给一次性爆发。
3. **乘法稀缺**——地品以上才有乘数，仙品以上才有指数。
4. **资源必须有出口**——每类产出都要有至少一个消耗途径。
5. **不惩罚离线**——闭关照常累计、队列照常推进、次数离线攒满。
